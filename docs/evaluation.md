# Guard evaluation

The guard is **action-chunk disagreement OR a stopwatch**, both set from good runs
only (ADR-005). This page reports it. Every other signal and rule we tried, and
why each lost, is in [experiments.md](experiments.md).

## Headline (ADR-005)

How much sooner the guard ends a failing run than a stopwatch would, both
held to the same 5% false-stop budget. The stopwatch stops any run that
outlasts the good calibration runs. Every failure in corpus A runs to the
280-step cap, so the stopwatch alone catches all of them. The guard is the
disagreement signal OR that stopwatch, both triggers set from good runs only
(`backstop.guard.stopwatch`). Spatial held-out half, 20 random splits,
paired: guard and stopwatch on the same split.

| | mean | 10th–90th percentile |
|---|---:|---:|
| **Saved over the stopwatch** | **13.4 steps (0.67 s)** | −1.4 to 25.9 steps |
| Held-out false-stop rate | 0.043 | 0.013 to 0.072 |
| Splits with no gain | 3/20 | |
| Failures caught | all | |

The stopwatch alone stops failures at step 135 on average (6.7 s). The
signal fires before it on about half the failures. On the other half
nothing in the signal separates the failure from a good run before the
clock runs out ("Is the failure visible at the onset?", below).

The stopwatch is strong here because every failure in this corpus is a
stall that runs to the cap. Where failures end early, a clock catches few
of them and the signal carries more of the result.

Reproduce with `just guard-reports` (`scripts/evaluate_guard.py` writes the
traces, then `scripts/evaluate_stopwatch.py`). The headline is written to
`artifacts/guard/headline/guard_eval.json`.

## Against a stopwatch

Every failure in corpus A runs to the 280-step cap. Successes finish by
about step 130. So a clock is already a guard: stop any run that is still
going at step N. Set from calibration successes at 5%, N is 132 (6.6 s).
That clock catches 41 of 41 held-out failures and stops 6 of 69 held-out
successes. Counting failures caught, no signal beats a timer here. What a
signal can add is an earlier stop.

### Is the failure visible at the onset?

At step t, take the signal's highest value so far. Compare failures with
the successes still running at t. 0.5 is a coin flip, 1.0 is perfect.

| step | successes running | disagreement |
|---:|---:|---:|
| 20 | 231 | 0.61 |
| 40 | 231 | 0.65 |
| 60 | 231 | 0.68 |
| 80 | 207 | 0.75 |
| 100 | 117 | 0.77 |

The reviewed onset of a no-grasp or failed-grasp episode is around step
40. There the signal sits at 0.65. A 5% line needs the worst successes to
sit below most failures, and at 0.65 they do not. So the late stop is
mostly a limit of the signal, not a badly placed line. Every other signal
tried, and even the privileged cup position, is just as late
(experiments.md, lessons 2).

### Does the guard just detect the perturbation?

Disagreement, one episode-level score per run. If the guard only reacted
to a changed scene, perturbed successes would score above clean ones.

| family | successes | perturbed success vs clean success | failure vs success, same family |
|---|---:|---:|---:|
| action_noise | 33 | 0.48 | 0.89 |
| camera | 29 | 0.41 | 0.88 |
| distractor | 33 | 0.41 | 0.92 |
| lighting | 35 | 0.45 | 0.92 |
| object_pose | 28 | 0.32 | 0.93 |
| language_paraphrase | 3 | 1.00 | 0.76 |

Perturbed successes look like clean successes. Failures in the same family
score higher. The exception is paraphrase: all 3 of its successes score as
abnormal, so rewording alone unsettles the policy. 3 runs is a direction,
not a rate.

### Does the 5% budget hold on held-out data?

The same comparison over 20 random 70/30 splits instead of one. Mean over
splits, 10th–90th percentile in brackets.

| rule | held-out false-stop | splits over 5% | detection | mean stop step |
|---|---:|---:|---:|---:|
| stopwatch only | 0.051 [0.014–0.087] | 10/20 | 1.000 | 135 (6.7 s) |
| disagreement OR stopwatch | 0.043 [0.013–0.072] | 8/20 | 1.000 | 121 (6.1 s) |

The OR rule (`backstop.guard.stopwatch`) is set from good runs only. The
line is the 4th-highest peak among 162 calibration successes. The clock
stops any run longer than the 4th-longest of them. Each trigger then has
at most a 4/163 chance of stopping a new good run, so the pair stays under
5% on average, with no grid and no failure used. Searched rules and
learned heads did not hold the budget this way (experiments.md, #7, #8).
With 69 held-out successes, one run is 1.4 points.

### The unseen suite, recalibrated from good runs

Object-suite successes are slower (median 153 steps), so the spatial clock
does not carry over either. The frozen spatial OR rule stops 17% of object
successes. Re-setting both triggers from n good object runs, with no
object failure used, 200 random draws each:

| good object runs | disagreement OR stopwatch false-stop | bound | mean stop step | signal first |
|---:|---:|---:|---:|---:|
| 10 | 0.172 | 0.182 | 123 | 82% |
| 20 | 0.093 | 0.095 | 143 | 78% |
| 30 | 0.058 | 0.065 | 163 | 71% |
| 40 | 0.041 | 0.049 | 177 | 65% |
| 50 | 0.035 | 0.039 | 188 | 60% |

The measured rate tracks the bound 2/(n+1) at every n. A new setting needs
about 40 good runs before the rule is inside 5%. The signal carries over.
The levels do not.

Reproduce with `uv run python scripts/evaluate_stopwatch.py`.
The numbers are written to `artifacts/guard/stopwatch/report.json`.

## Visual precondition: a per-object detector gate

The check asks one question before the arm moves: is the instructed object
in the first frame? It uses an open-vocabulary detector (OWLv2,
`google/owlv2-base-patch16-ensemble`) and gives each object its own line
(`backstop.guard.presence`). The line is set only from frames that show
that object: below the k-th lowest of them, the object is called missing.
That bounds how often a frame with the object present is stopped, k/(n+1),
without ever needing a missing-object example. An object with no reference
frames is reported as unverified, never guessed.

One line for every object does not work. A real tomato-sauce can scores
0.01 and a moka-pot lookalike on the spatial table scores 0.3. The CLIP and
SmolVLM2 attempts failed for the same reason (docs/experiments.md, #6a).

References: the black bowl from the 162 spatial calibration successes.
The moka pot from 40 rendered LIBERO-10 scenes that contain one
(`scripts/render_reference_frames.py`), because corpus A never shows one.
Each grocery item from half the object-suite scenes that contain it.

### The missing-object runs

| | result |
|---|---:|
| missing moka pot (`language_absent`) stopped at step 0 | **28/30** |
| spatial held-out good runs stopped (black bowl present) | 2/69 |
| object-suite runs not used as references stopped (instructed item present) | 8/60 |
| same 30 runs, headline guard (disagreement OR stopwatch) | median stop step 86 (4.3 s) |

The gate stops 28 of the 30 missing-object runs before the arm moves. The
headline guard catches them too, but only once the policy starts to waver,
about 4 seconds in. The 2 misses score 0.298 and 0.310 against a line of
0.291: the lookalike on the table. The margin is thin. Two of the 40
rendered moka pots score 0.290 and 0.291, so a real moka pot and the
lookalike overlap at the bottom. The other 38 score 0.33 or more. The 8
object-suite stops come from grocery lines set on other layouts (below).

`language_absent` stays out of the headline (ADR-004): its instruction
names an object that no good run ever names. The gate is reported here on
its own, not added to the headline guard. On corpus A's other runs the
object is always present, so the gate could only add false stops there.
Adding it to a deployed guard means giving it a share of the 5% budget.

### Where the detector works and where it does not

Same object name, frames that show it against frames that do not. "Other
scene" means a scene of the other suite. "Same scene" means an object-suite
scene that lacks the item, beside the ones that have it. Scene contents
come from the LIBERO task files, for scoring only. The `distractor` family
adds a milk carton to spatial scenes, so those count as milk present.

| object | present, other scenes, wrongly flagged | missing, other scene, caught | missing, same scene, caught |
|---|---:|---:|---:|
| black bowl | — | 100/100 | — |
| moka pot | — | 388/400 spatial, 100/100 object | — |
| bbq sauce | 4/30 | 400/400 | 40/40 |
| chocolate pudding | 0/30 | 0/400 | 40/40 |
| orange juice | 19/30 | 400/400 | 40/40 |
| ketchup | 18/30 | 400/400 | 30/40 |
| salad dressing | 10/30 | 400/400 | 24/40 |
| milk | 10/30 | 343/350 | 9/40 |
| butter | 0/30 | 320/400 | 0/40 |
| alphabet soup | 19/30 | 0/400 | 2/40 |
| cream cheese | 0/30 | 0/400 | 0/40 |
| tomato sauce | 1/30 | 0/400 | 0/40 |

Three things this shows.

- **The detector tells rooms apart better than objects.** A distinctive
  object missing from a different kind of scene is caught almost every
  time: no black bowl in the grocery scenes, no ketchup on the spatial
  table. Telling one grocery carton from another in the same scene works
  for 3 of 10 items.
- **Some objects it cannot see at all.** Alphabet soup, cream cheese and
  tomato sauce score near zero even when they are in plain view.
- **A line does not carry over to new layouts, even for the same object.**
  The "present, other scenes" column sets each grocery line from 3 scenes
  and checks it on the other 3. Ketchup, orange juice and alphabet soup
  then stop well over half their present frames. The score moves with
  where the object sits and what covers it. The spatial gate works because
  its references cover the same 10 layouts it runs on. The reference
  frames have to come from the setting the guard runs in, the same lesson
  as the stop lines in "Against a stopwatch".

Splitting the grocery references by scene matters. A split by frame puts
near-copies of one layout on both sides, since the 10 runs of a task open
on almost the same scene, and it makes the wrongly-flagged column look
like 0–6 of 30.

Reproduce with `uv run python scripts/render_reference_frames.py`, then
`uv run python scripts/evaluate_presence.py` (GPU, about 3 minutes).

## Experiments that did not make it

Temporal self-consistency, progress monitoring, a one-line visual check
(CLIP, SmolVLM2, detector), a learned trust head, persistence rules, signals
from recent papers, a line that follows a typical success, the model's own
activations, a per-step model, the privileged cup position, and per-signal
object-suite cutoffs. Each has its question, method, numbers and verdict in
[experiments.md](experiments.md). Their code is kept at the git tag
`research-archive-2026-10`.
